1. LATAR BELAKANG
------------------
Ditemukan lewat investigasi kode + tes langsung ke API (bukan dugaan):
halaman kasir (`/app/pos`) memanggil pencarian produk dengan parameter
`in_stock=true` (lihat `app/[locale]/app/pos/page.tsx` fungsi
`searchProducts`, memanggil `getProducts(..., true)` di
`lib/api/app/product.ts:73-97`). Di `lib/modules/pos/products/admin.service.ts:165-172`,
parameter ini diterjemahkan jadi filter Prisma:

    if (inStockOnly === 'true' && branchUuid) {
      where.stockItems = { some: { branchUuid, stock: { gt: 0 } } };
    }

Efeknya: produk dengan stok 0 di cabang itu HILANG TOTAL dari hasil
pencarian kasir -- bukan cuma tidak bisa dibeli, tapi tidak muncul sama
sekali. Kasir yang mencari produk itu akan mengira produknya belum
tercatat di sistem, padahal datanya ada. Sudah dites langsung ke API dev
(`in_stock=true` di branch manapun saat semua 41 produk dummy berstok 0
-> hasil 0 produk sama sekali), jadi ini bukan cuma kasus tepi.

Filter yang sama juga TIDAK punya pengecualian untuk `kind` produk --
produk `jasa`/`digital` (yang menurut desain memang TIDAK PERNAH punya
baris stok sama sekali, lihat komentar di
`lib/modules/pos/transactions/admin.service.ts:187-189` dan
`lib/modules/pos/products/product.mapper.ts:74-81` yang selalu
menghasilkan `total_stock: 0` kalau tidak ada `stockItems`) IKUT
KETUTUP dari pencarian kasir. Ini jelas salah -- jasa/produk digital
harusnya selalu bisa dicari & dijual, tidak tergantung stok sama sekali.

Bug KEDUA yang menumpuk di halaman yang sama: tombol "tambah ke
keranjang" di hasil pencarian (`app/[locale]/app/pos/page.tsx:811`)
di-disable dengan `disabled={stock <= 0}` TANPA memandang `kind` --
padahal baris di sebelahnya (baris 838-843) sudah punya UI yang benar
untuk kasus ini: kalau `product.kind !== 'barang'` ditampilkan label
"Tanpa stok" (bukan angka stok), yang secara desain berarti "konsep
stok tidak berlaku, harusnya selalu bisa ditambahkan". Disable
unconditional ini bikin jasa/digital juga tidak bisa ditambahkan ke
keranjang kalau (seperti biasanya) `total_stock`-nya 0.

User sudah setuju arah perbaikan bug pertama: produk TETAP TAMPIL di
pencarian kasir walaupun stoknya 0 (hapus/ubah filter `in_stock`, bukan
sembunyikan). Tapi soal BOLEH/TIDAKNYA transaksi dengan stok 0, user
mau itu jadi SETTING per company (bukan hardcoded selalu boleh atau
selalu tidak boleh) -- pendekatan yang disepakati: setting-nya di
LEVEL COMPANY (bukan per-produk).


2. MASALAH DESAIN YANG PERLU DIKONFIRMASI DULU KE USER
---------------------------------------------------------
Sebelum coding, WAJIB tanya user (jangan asumsi/tebak, ini keputusan
produk):

a) Nama & lokasi setting. Usulan: kolom baru di model `Company`
   (`prisma/schema.prisma`), misal `allowNegativeStock Boolean @default(false)`.
   `Company` adalah tabel administrator SaaS (bukan tabel tenant app),
   jadi TIDAK perlu prefix `app_`/`company_uuid` sesuai aturan CLAUDE.md
   soal itu -- kolom ini langsung melekat di baris company itu sendiri.
   Default `false` (tidak boleh stok minus) supaya perilaku default
   konsisten dengan ekspektasi kebanyakan toko & tidak mengubah perilaku
   existing secara diam-diam untuk company yang belum sempat atur
   setting-nya.

b) Di mana admin tenant mengatur setting ini? Dua opsi:
   - Tempelkan ke endpoint & halaman company profile yang SUDAH ADA
     (`app/api/app/company/route.ts` PUT, schema
     `updateTenantCompanySchema` di `lib/validations/company.ts`,
     halaman `app/[locale]/app/company/page.tsx`) -- paling murah, tapi
     "boleh stok minus" secara konsep lebih ke pengaturan POS daripada
     profil perusahaan.
   - Buat bagian "Pengaturan POS" terpisah (belum ada saat ini) --
     lebih rapi secara IA tapi nambah endpoint & halaman baru.
   REKOMENDASI: mulai dari opsi pertama (tempel di company profile) dulu
   karena settingnya baru satu ini, kecuali user sudah berencana bikin
   halaman "Pengaturan POS" untuk hal lain juga.

c) Permission apa yang menggerbangi endpoint update setting ini?
   Kemungkinan cukup permission `company.update` yang sudah dipakai
   endpoint company yang ada, KECUALI user mau permission baru khusus
   (misal `pos.settings.update`) supaya bisa dipisah dari izin edit
   profil perusahaan.

d) Pesan error saat transaksi ditolak karena stok kosong & setting
   `false` -- apakah pesan sekarang (`Stok {uuid} tidak cukup (tersedia: X)`
   di `lib/modules/pos/transactions/admin.service.ts:209`) sudah cukup,
   atau perlu dibedakan pesannya supaya kasir paham ini soal kebijakan
   company, bukan bug?

e) Kalau setting `true` (boleh stok minus): apakah stok BOLEH turun
   sampai negatif tanpa batas, atau tetap perlu batas bawah (misal tidak
   boleh lebih negatif dari suatu angka)? Asumsi awal: tanpa batas bawah
   (paling sederhana), TAPI konfirmasi ke user karena ini bisa berdampak
   ke laporan stok/nilai persediaan.


3. DESAIN SOLUSI (garis besar, detail final menyesuaikan jawaban poin 2)
----------------------------------------------------------------------------

3a. Bug hilang dari pencarian (independen dari setting, SELALU diperbaiki):
    - Hapus pengiriman `in_stock=true` dari pemanggilan
      `getProducts(...)` di `searchProducts` (`app/[locale]/app/pos/page.tsx`).
      Endpoint & filter `in_stock` di
      `lib/modules/pos/products/admin.service.ts` boleh TETAP ADA (siapa
      tahu dipakai tempat lain / berguna untuk kasus lain), yang berubah
      cuma pemanggil dari halaman kasir.
    - Tombol tambah-ke-keranjang: ubah `disabled={stock <= 0}` di
      `app/[locale]/app/pos/page.tsx:811` jadi kondisional berdasar
      `kind` DAN setting company:
        - `kind !== 'barang'` -> TIDAK PERNAH disable karena stok (selalu
          boleh, sesuai desain "Tanpa stok" yang sudah ada).
        - `kind === 'barang'` -> disable kalau `stock <= 0` DAN setting
          `allowNegativeStock` company === false. Kalau setting true,
          tetap boleh ditambahkan (opsional: tampilkan indikator visual
          "stok akan minus" biar kasir sadar, detail UI didiskusikan
          lagi kalau perlu).
    - Fungsi `addToCart` (baris ~218-240 di file yang sama) juga perlu
      cek yang sama -- saat ini ada guard `if (stock <= 0) { ...; return; }`
      yang perlu disesuaikan supaya konsisten dengan tombol.

3b. Setting company & enforcement server-side (WAJIB, jangan cuma UI):
    - Tambah kolom `allowNegativeStock` (nama final tergantung poin 2a)
      ke model `Company` di `prisma/schema.prisma` + migration BARU
      (lihat catatan production di atas -- JANGAN edit migration lama).
    - `lib/validations/company.ts`: tambah field ke schema update yang
      relevan (tergantung jawaban poin 2b, apakah `updateTenantCompanySchema`
      atau schema baru).
    - `lib/modules/companies/app.service.ts`: update service company
      untuk baca/tulis field baru ini, mapper response perlu include
      field ini (snake_case di API, sesuai aturan CLAUDE.md).
    - PENTING -- validasi stok WAJIB diubah di server, bukan cuma
      disable tombol di client (kalau tidak, siapa pun bisa POST
      langsung ke API dan bypass client). Titik enforcement utama:
      `lib/modules/pos/transactions/admin.service.ts:197-211` (loop
      cek stok sebelum create sale) -- baca `company.allowNegativeStock`
      (via `context`/query company yang sudah tersedia di scope function
      ini) dan skip pengecekan `stock.stock < item.quantity` kalau
      settingnya true DAN `tracksStock(item.productUuid)` true (kalau
      false / jasa-digital, memang sudah selalu di-skip, tidak berubah).
    - Cek juga apakah ada titik enforcement stok lain yang perlu
      perlakuan sama (misal endpoint retur/refund penjualan, atau modul
      lain yang mengurangi stok saat create sale) -- grep
      `stock.*<.*quantity\|stock < item` di `lib/modules/pos/` sebelum
      mulai coding untuk pastikan semua titik konsisten.
